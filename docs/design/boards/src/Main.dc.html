Modernization: eleven screens, two paths, one flow

A bank keeps OBDX and gives its screens premium components, or it moves the UI to another technology module by module. The OBDX server and its services stay exactly as they are on both paths. Every screen below is drawn in the factory's own design system and shell, and every action is listed on the Actions and links map.

The flow

1 Overview→ 2 Choose a path→ UI path3 Component inventory→4 Component mapping→Upgrade plan Migration5 Technology catalogue→6 Migration planner → 7 Workspace→ 8 Validation→ 9 Review and approval+Decisions→ 10 History

Both paths end in an ordinary factory change, so Workspace, Validation, Review and History serve both: the UI path changes components in the JET code, the migration path writes the new app.

How it fits the factory as it is built

  • Menu: one entry, Modernization, under Modernize. It folds open four pages, the way Administration does: Overview, Component factory, Technology settings and History. The steps of each path are reached from the flow, not the menu. The top bar (workspace, search, theme, bell, help, account) is unchanged.
  • Pages: one page module per screen (views/modernization-*.html and its view model), registered in appController.js under the modernize group; the breadcrumb row is the factory's own.
  • Elements: bx-select for the pickers, fx-menu-button for every ⋯ menu, fx-sheet for the side panels, fx-table rows, ui.status() chips, the ring chart, tab strips from strips.js.
  • Look: only --fx-* tokens, so the dark theme works; radius sm, lg, xl and pill; motion from the --fx-dur-* tokens.
  • Feedback: Analyze, Run the tests and Write it again use busy.js: the button spins and the top progress bar runs.
  • Reuse: the code view and diff reuse the Changes page's diff; Validation reads the same Jenkins results as Build, Test & Review; Review uses the change's existing approval steps.

Server and data

  • Component inventory: the analysis counts each oj-* element per screen and module from the code index.
  • Component packs: four packs from one bank design system, under target-packs/components/: Premium Oracle JET (bx- elements, all 176 components), React, React Native and Angular (preview). A metadata registry and a JET mapping registry (six statuses, each with evidence) drive the Component factory; a pack shows a component as Available only when its checks pass. A factory update brings a new version; moving screens to it is proposed as a change, never applied by itself.
  • Component style: the design option, motion and theme chosen in the Component factory are saved per workspace; Technology settings shows them, and new code and pack upgrades use them.
  • Progress: a module counts as moved only when its change is delivered to SVN. The planner's weeks are the team's own plan. No estimated days, risk scores or star ratings.
  • Records: the plan (modules, order, weeks) and the chosen path are saved per workspace: a new Flyway migration, V34.
  • OBDX rules: every converted module is checked against the 8 rules: same digx services, session cookie through OHS, nonce from /digx/v1/session/nonce, server-driven 2FA, masked tokens, password encryption, role menus, labels and validations.
  • Models: only the conversion and the assistant call a model, through Models & AI as today.

Decided, and set aside

  • Technologies: React and React Native (packs ready), Angular (next), JET Core Pack, Vue 3, Flutter for mobile, native Swift and Kotlin, Capacitor.
  • Not offered: Next.js server rendering, Flutter Web, SvelteKit, Blazor, .NET MAUI, each with its reason in the catalogue.
  • Wording: results come from the analysis, Jenkins or the factory's checks, so no panel is called "AI" unless a model wrote it.
  • Deferred: OBDX version upgrades (22.x to 25.x).
  • Open: the screenshots used a top menu bar. These boards keep the factory's left menu so every page stays the same; moving the whole factory to a top bar would be a separate decision.
  • The numbers on the boards are examples to show the layout.
